# 0004. 具体型を優先し typing の抽象化機構を制限する

- 日付: 2026-09-11
- ステータス: 採用

## 背景

このリポジトリは新規プロジェクトの雛形であり、生成直後のコードは `sample_add` 程度の規模しかない。この状態で `Protocol` や `TypeVar` による汎用化、将来の拡張を見越した基底クラスやプラグイン機構を書くと、実装が 1 つしかないのに抽象だけが存在する構造が派生プロジェクトすべてに複製される。

型チェッカーとして `ty` を導入したが、型エラーの解消手段には幅がある。`cast` や `# ty: ignore` は短時間で緑にできる一方、型の不一致という情報そのものを消してしまう。どの手段を正とするかを決めておかないと、テンプレートの利用者ごとに判断がぶれる。

`select = ["ALL"]` のため ANN401(`Any` の使用)は既定で有効だが、抑制すること自体は容易であり、規則としてどう扱うかを明示する必要があった。

## 検討した選択肢

- **型の書き方に規則を設けない**: Ruff と `ty` が通ればよしとする。書き手の裁量は最大だが、テンプレートから派生した各プロジェクトで方針がばらつき、`cast` による握りつぶしを止める根拠がない
- **抽象化機構を全面禁止する**: 判断は単純になるが、実際に異なる型の実装を複数受け取る場面(将来的に発生しうる)で回避策を強いることになり、規則の方が壊れる
- **具体型を既定とし、抽象化には「実装が複数あること」という条件を課す**: 組み込み型・標準ライブラリの型・自作クラス・`X | None`・`list[str]` などを既定にし、`TypeVar` / `Generic` / `Protocol` / `overload` / `TypeAlias` / `cast` / `TYPE_CHECKING` は異なる型の実装を実際に複数受け取る箇所に限る

## 決定

3 つ目を採用し、CONTRIBUTING.md の「型ヒント」「設計方針(必要十分)」節に規則として記載した。

- 関数シグネチャには公開・非公開を問わず型ヒントを書く。使う型は具体型に限る
- `typing` の抽象化機構は、異なる型の実装を実際に複数受け取る箇所でのみ使う。実装が 1 つしかないものを汎用化しない。`Any` は禁止(ANN401)
- 型エラーは具体型の修正で解決する。`cast` や `# ty: ignore` で黙らせない。抑制する場合は理由コメント付きの最終手段とする
- 同じ基準を型以外にも広げ、将来の拡張を見越した基底クラス・インターフェース・プラグイン機構・レジストリ・設定の外部化・ラッパー層・汎用ユーティリティは、具体的な利用者が 2 つ以上現れるまで導入しない

抽象を「禁止」ではなく「利用者が 2 つ以上」という閾値で制御するのは、必要になった時点で導入できる余地を残しつつ、先回りの汎用化だけを止めるためである。

## 結果

- PR テンプレートのチェックリストに「typing の抽象化機構や将来を見越した抽象を新たに導入していない(導入した場合は理由を変更概要に書いた)」を追加した。閾値の判断をレビューの場に載せる
- `/quality-check` skill の型エラー対処方針を「具体型の修正で対応し、`cast` / `TypeVar` / `Protocol` や `# ty: ignore` で回避しない」に揃えた。人間と AI エージェントが同じ基準で直す
- 規則は CONTRIBUTING.md と AGENTS.md の双方に書かれているため、変更時は同一 PR で同期させる
- 型情報を配布しない判断(`py.typed` の削除)は別の軸の判断として ADR 0005 に分けた
