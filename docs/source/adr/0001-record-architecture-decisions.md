# 0001. 設計判断を ADR として記録する

- 日付: 2026-09-14
- ステータス: 採用

## 背景

開発規則は CONTRIBUTING.md(および AI エージェント向けの AGENTS.md)に書かれているが、**その規則をなぜ採用したか** や **検討して退けた選択肢** は残らない。時間が経つと規則の妥当性を再評価できず、同じ議論を繰り返したり、理由を知らないまま規則を壊したりしやすい。Claude Code などの AI エージェントも、過去の判断を参照できなければ規則に反する提案をしてしまう。

## 検討した選択肢

- **CONTRIBUTING.md に理由も書く**: 一か所で済むが、規則の一覧に経緯が混ざって読みにくくなり、退けた選択肢まで書くと肥大化する
- **PR の説明文に残す**: 既に行っているが、PR 単位で散らばり、後から探しにくい
- **ADR (Architecture Decision Record) を `docs/source/adr/` に置く**: 判断ごとに 1 ファイルで、Sphinx ドキュメントとして公開でき、`invoke adr` で定型化できる

## 決定

ADR を採用する。`docs/source/adr/NNNN-<slug>.md` に日本語で「背景 / 検討した選択肢 / 決定 / 結果」を書き、`uv run invoke adr` で作成する。CONTRIBUTING.md には規則を、ADR には理由を書く役割分担とする。

## 結果

- 開発規則・ツール構成・依存の採否・アーキテクチャに関わる判断を伴う PR では ADR を追加する(PR テンプレートのチェックリストに含める)
- 採用済みの ADR は書き換えず、新しい ADR で置き換える(履歴として残す)
- ADR は API リファレンスと同じ Sphinx サイトに載るため、`invoke docs --strict` の対象になる
